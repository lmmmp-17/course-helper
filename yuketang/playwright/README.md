# Playwright 版：技术说明

**怎么装、怎么用，见仓库根目录 [README 的初级使用教程](../README.md#一初级使用教程)。** 这里记录的是在真实页面上观察到的东西、做法背后的原因，以及还没确认的地方。

用你本机的 Chrome 或 Edge 打开长江雨课堂「学习空间」，像人一样点开视频、放完、换下一个。观看记录由平台自己的播放器上报，这里不调用任何接口。

和 [`legacy/main.py`](../legacy/main.py) 是两条完全不同的路：`main.py` 不播放视频，直接往 `/video-log/heartbeat/` 发自己拼出来的心跳。这个版本什么都不拼，所以不存在“请求长得像不像”的问题。

## 为什么不在 main.py 上改

在真实页面上观察播放器自己发出的请求（只读监听，不拦不改），能看到 `main.py` 改请求头、改节奏都补不上的差别：

- 播放器每 30 秒发一次 `/video-log/heartbeat/`，一次装 6 条 `et: "heartbeat"`，每条间隔 5 秒；`main.py` 每 5 秒单发一条，事件类型在 `playing` / `waiting` 里随机挑，从不出现 `heartbeat`
- 心跳里的页面标识 `pg` 每次加载页面都是随机的（实测 `48994152_166bb`），`main.py` 写死成 `{视频ID}_q8mn`
- 页面同时还在发 `/video-log/log/track/` 的 `ai_agent_hb` 事件（数字人 / AI 面板的心跳），`main.py` 完全没有
- 真实播放会持续从 CDN 拉视频分片；`main.py` 只读视频开头几 KB 拿时长
- 图文：真实页面一打开就自己调用 `user_article_finish`，同时还有二十来个别的请求（`leaf_info`、`add_study_node_and_leaf_h5`、AI 学伴的一串）；`main.py` 等 3 秒后单独调这一个接口
- `main.py` 默认 3 个视频并发、1.5 倍速；同一个账号同时在“看”三个视频，这一条本身就说明问题

另外，现在课程用的是新版「学习空间」（`/ai-workspace/lms-graph/...`），`main.py` 针对的是旧版的 `/v2/web/xcloud/video-student/...` 页面。

## 它做什么

- 读左侧「知识点」目录，从当前项往后找第一个没完成（没有圆圈勾）的视频或图文。课堂（直播回放）不碰。
- 有学习项的知识点如果是折叠的，里面的学习项根本不渲染（实测一门课 111 项里有 24 个视频藏在折叠节点下），所以走到它时先点展开图标，再接着往下找。不会一上来把所有节点都展开。
- 视频：起播前静音，真实点击课件中间的大播放按钮；暂停了就恢复，被弹窗打断就停下交给你；放完之后看目录上有没有打勾。已经放完的不重放。
- 图文：实测页面一打开就记为已读（内容是 Office Online 嵌入的课件）。脚本仍然停留一段时间（默认 25–70 秒），期间用真实滚轮往下翻，不会点开就走。
- 所有点击、滚轮都是浏览器自己构造的可信事件（CDP 输入），带贝塞尔轨迹和人手量级的按键间隔；等待时长全部抖动；播放期间偶尔动一下指针。
- 焦点模拟：窗口放到后面不会触发 blur。别把学习页切成同一窗口里的后台标签，`visibilityState` 没法模拟。

## 在真实页面上确认过的

- 放完一个 15 分钟的视频，目录上打勾、标题栏变成「已完成」；中途没有暂停、没有弹题。
- 视频完成后平台刷新进度会重新渲染目录，有一小段时间读不到，脚本会等它渲染完。
- 切到一个 31 分钟的视频时，CDN 约 50 秒才给数据（播放状态、`readyState` 1、`seeking`）。这时脚本只等着，不去点那个播放/暂停二合一的按钮；缓冲超过 2 分钟才停下。
- 点展开图标会展开知识点，不会切走当前项。

## 两套播放器

这门课里混着用，适配时两套都要认：

| | 数字人播放器 | xtplayer |
| --- | --- | --- |
| 容器 | `.digital-human-player-box` | `.xtplayer` |
| 视频 | `video#video` | `video.xt_video_player`（id 动态生成，不能按 id 选） |
| 大播放键 | `.play-status-box` | `.xt_video_bit_play_btn` |
| 控制栏 | `.control-box` | `.xt_video_player_controls` |
| 倍速 | `.rate-config-item`（`2x`） | `.xt_video_player_speed .xt_video_player_common_list li`（`2.00X`） |
| 音量 | `.volume-btn` | `.xt_video_player_volume .xt_video_player_common_icon` |

两套都提供到 2x。注意清晰度菜单（高清/标清）和倍速菜单共用 `common_list` 类名，倍速要限定在倍速按钮里面。

## 还没确认的

- 视频播放中会不会弹题。脚本遇到弹窗会停下，不替你点。
- 数字人播放器的音量按钮没实测过（代码只在 `muted` 被撤销时才会去点它，而那套播放器不撤销）。
- 静音在两套播放器上方式不同：数字人播放器设 `video.muted` 就行；xtplayer 有个看门狗，会在一两秒内把外部设的 `muted` 改回去（实测事件序列 `pause → volumechange → play → volumechange`），只能点它自己的音量按钮——点一下 `volume` 归零并且保持得住。代码先试前者，被撤销再退到后者。
- 同一个看门狗也会撤销 `video.pause()`：脚本退出后视频会继续播，要停得自己在页面上暂停或关掉标签页。

## 节奏与「用户激活」

这两条来自本地检测靶场（`~/work/cx-detect-lab`，全程离线，另一个会话搭的）实测出来的真人基线。

**停顿的分布形状**。以前所有等待都是「区间内均匀取值」加 8% 的长尾，变异系数（标准差/均值）只有 0.17~0.28；靶场测到真人连续操作的间隔是 0.45~0.49。同样是随机，分布形状不是一回事——真人的停顿是「多数偏短、偶尔拖很久」。现在 `human.mjs` 改成对数正态取样：配置值当中位数，下限仍是配置的下限（不会比你设的还快），上限封顶 3 倍只为挡极端值。实测变异系数约 0.46。

**开场先真实地动一下**（`settleIn`）。被调试端口接管的浏览器里，`navigator.userActivation.hasBeenActive` 会在页面加载约 1.5 秒后自行变成 true，普通 Chrome 则要等真实交互——靶场里 Playwright 自己启动和接管已有 Chrome 两种方式表现一致。于是出现一个自相矛盾的状态：浏览器说用户激活过，页面却一个可信输入事件都没收到。而以前 1.2~5.5 秒的启动延迟反而让这个状态一直挂着：**越是加「像人的延迟」，这个窗口开得越久**。现在接管页面后先移动指针、小幅滚一下再滚回来（滚轮同样是可信输入，但不会点到任何东西），把这个状态合上，之后再走原来的启动延迟。

## 测试

```bash
npm run test:unit   # 不需要浏览器
npm test            # 单元 + 端到端（需要本机 Chrome）
```

端到端测试的桩页面照真实页面的结构搭，只接受 `isTrusted` 的事件，合成事件一律记进 `rejected` 且不产生效果。
